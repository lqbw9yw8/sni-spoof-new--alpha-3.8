## بخش ۱ — بازرسی کامل (۶ گام اجرایی)

### گام ۱ — اجرای واقعی تست‌ها (این بار در محیطی که کامپایلر دارد)

قبلی‌ها بدون زنجیرهٔ Rust نوشته و ادعا شدند. این بار:

```bash
cargo fmt --all -- --check
cargo clippy --all-targets -- -D warnings
cargo test --all-targets
cd uitest && npm install && npm test   # ۶ سوئیت jsdom
```

الزامات:
- هر عددی که در گزارش می‌آید باید از خروجی **همین اجرا** آمده باشد، نه از
  فایل‌های STATUS/TEST_MATRIX قبلی.
- خلاصهٔ خروجی هر دستور (تعداد پاس/شکست، خطای کامپایل) عیناً در گزارش ثبت شود.
- اگر محیط فاقد کامپایلر است: اول تمام تلاش برای نصب انجام شود؛ اگر نشد،
  راه جایگزین (مثل اجرای `ci/github-actions.yml` روی GitHub Actions) به کار
  برود و نتیجهٔ واقعی آنجا خوانده شود؛ اگر هیچ راهی نبود، با صدای بلند
  «NOT TESTED — دلیل: …» نوشته شود.

### گام ۲ — هماهنگی بین‌ماژولی با `gen_status.py` و تطبیق خط‌به‌خط

```bash
python3 tools/gen_status.py
git diff --stat          # TEST_MATRIX.md بازتولیدشده نباید با کامیت‌شده اختلاف داشته باشد
```

سپس تطبیق **خط‌به‌خط** این پنج لایه — هر ناهماهنگی با شمارهٔ فایل و خط:
1. `src/config.rs` — ساختار `Settings` (فیلد، پیش‌فرض، `validate`)
2. `src/webui/index.html` — کنترل‌های UI و `id`ها
3. `uitest/mock-server.mjs` — پیش‌فرض‌ها و schemaی موک
4. `dpi_guard.toml.example` — نمونهٔ کانفیگ
5. فهرست پروفایل‌ها (۷ پروفایل از جمله `NestedCloak`) — باید در همهٔ
   لایه‌ها (اعتبارسنجی config، UI، mock، toml) یکسان باشد.

### گام ۳ — تست تداخل جفت‌تکنیک‌ها

درس‌هایی که از باگ‌های قبلی گرفتیم — هر جفت باید تست اختصاصی داشته باشد،
و اگر ندارد، **در همین نشست نوشته و اجرا شود**:

- **مُهر ECH آخرین تغییر باشد:** وقتی ECH واقعی مسلح است، مُهر (seal) باید
  روی نسخهٔ نهایی هللو زده شود — بعد از uTLS، Geedge و پدینگ — چون AAD کل
  هلوی بیرونی را می‌پوشاند.
- **نشت `0xFF01`:** در NestedCloak + ECH، هیچ نسخه‌ای از SNI واقعی (رکورد
  `0xFF01` در هلوی داخلی یا بیرونی) نباید روی سیم Representation روشن داشته
  باشد.
- **بازچینی با `tcp_seq`:** قطعات فرگمنت باید با شماره‌های توالی درست، بدون
  هم‌پوشانی و بدون شکاف بازچینی‌پذیر توسط DPI باشند.
- **fail-open:** خطای پردازش در هیچ تکنیکی نباید باعث بلعیده‌شدن یا حذف
  پکت شود؛ مسیر خطا باید پکت را دست‌نخورده عبور دهد.

حداقل ماتریس جفت‌ها برای بازبینی/تست: ECH×uTLS، ECH×Geedge، ECH×Fragmentation،
ECH×Padding، NestedCloak×ECH، Fragmentation×TCP-fooling، QUIC×تکنیک‌های TCP،
fail-open×همهٔ مسیرهای خطا.

### گام ۴ — انطباق سیمی با RFCها

مرور نقطه‌به‌نقطهٔ توابع serialize/parse در `ech.rs`، `hpke.rs`،
`fragmentation.rs`، `utls.rs`، `quic.rs`، `packet.rs`، `http_host.rs` در برابر:

| RFC | موضوع | نقطهٔ بازبینی |
|---|---|---|
| RFC 8446 | TLS 1.3 / ساختار ClientHello | framing رکورد و هندشیک |
| RFC 6066 | SNI | فرمت `server_name` (tag 0x0000) |
| RFC 7685 | پسوند padding | فرمت `padding_extension` |
| RFC 8701 | GREASE | مقادیر و جای‌گذاری معتبر |
| RFC 9180 | HPKE | KEM/KDF/AEAD، encapsulated key، بردارهای تست |
| RFC 9849 | ECH | outer/inner hello، AAD، `config_id`/`enc`، HPKE suite |

هر انحراف از سیم استاندارد: یا باگ است (فهرست شود) یا عمدی است (باید در کد
کامنت و در گزارش توجیه شود).

### گام ۵ — صداقت مستندات

- هر ادعای «اجرا شد / پاس شد / DONE» در `STATUS.md`، `README.md` و
  `CHANGELOG.md` باید یا مدرک اجرای **همین نشست** داشته باشد یا اصلاح شود.
- اعداد STATUS.md (تعداد تست‌ها، فیلدها، کنترل‌ها) با شمارش واقعی
  (`gen_status.py` + شمارش `#[test]`) تطبیق داده شود.
- ستون «تست اجراشده» فقط با خروجی واقعی cargo/jsdom پر می‌شود.

### گام ۶ — قواعد کد

- `unsafe` فقط در `engine.rs` و `singleton.rs` (باقی crate زیر
  `#![deny(unsafe_code)]`).
- طول خط ≤ ۱۰۰ کاراکتر در همهٔ فایل‌های Rust.
- هر ماژول `src/*.rs` تست در همان فایل دارد (استثنای مستند: `engine.rs` — FFI).
- هیچ `todo!()` / `unimplemented!()` / تابع همیشه-`Err` بی‌برچسب `STUB`.
- ابزار کمکی برای شمارش خطوط بلند مجاز است؛ نتیجهٔ آن باید تکرارپذیر باشد.

## بخش ۲ — ۱۰ ایدهٔ تکنیک جدید (قالب ارزیابی)

هر ایده دقیقاً با این قالب ارزیابی شود — هیچ فیلدی خالی نماند:

```markdown
### تکنیک N — <نام>
- **مرجع پژوهشی:** RFC / پیش‌نویس IETF / مقاله / پروژهٔ مرجع
- **مکانیزم:** دقیقاً چه بایت‌هایی روی سیم (کدام فیلد کدام لایه) تغییر می‌کند
- **چرا DPI را می‌شکند:** مدل DPI هدف و فرضی که می‌شکند
- **ریسک ناسازگاری با سرور:** کدام پیاده‌سازی سرور ممکن است رد کند/ریسک قطع‌شدن
- **سختی:** کم / متوسط / زیاد + برآورد حجم کد و ماژول‌های درگیر
- **طرح تست:** تست واحد + تست سیم + ستون‌های TEST_MATRIX مرتبط
- **وضعیت پیشنهادی:** پیاده‌سازی فوری / پس از آزمون میدانی / فقط پژوهش
```

| # | تکنیک | چرا قوی است |
|---|---|---|
| ۱ | تصادفی‌سازی ترتیب اکستنشن‌ها در هر اتصال | استخراج‌کننده‌های آفست‌محور را می‌شکند؛ سرورها ترتیب را نادیده می‌گیرند |
| ۲ | GREASE در cipher-suiteها + ترتیب تصادفی سایفر | پارسرهای سخت‌کدشدهٔ DPI گیج می‌شوند |
| ۳ | SNI چندتایی (بی‌خطر اول، واقعی دوم) | DPIهایی که فقط اولین ورودی را می‌خوانند |
| ۴ | واکشی خودکار ECHConfig از DoH/SVCB | حذف hex دستی؛ فعال‌سازی خودکار ECH واقعی |
| ۵ | تصادفی‌سازی اثرانگشت هدر TCP/IP | طبقه‌بندی بر اساس fingerprint بی‌اثر می‌شود |
| ۶ | جیتر زمانی تطبیقی (یادگیری تایم‌اوت باف DPI) | دقیقاً دور آستانهٔ بازچینی DPI بازی می‌کند |
| ۷ | فریب QUIC (Version Negotiation/Retry جعلی) | پارسرهای QUIC Initial را می‌شکند |
| ۸ | استتار آماری ضد DPI یادگیرنده (ML) | شبیه‌سازی آماری ClientHello مرورگر بی‌خطر |
| ۹ | دکوی نسخهٔ رکورد/هندشیک | پارسرهای سخت‌گیر DPI به بن‌بست می‌روند |
| ۱۰ | پنهان‌سازی با ازسرگیری نشست (PSK/0-RTT) | حذف SNI قابل‌اتکا برای DPI |

## قواعد اجرایی (تعهد الزامی این نشست)

1. **کار فقط روی شاخهٔ نشست** (`arena/…`) — هیچ push به شاخهٔ دیگر، هیچ
   تغییر روی `main`.
2. **هر تکنیک پیاده‌شده** = پرچم **خاموش پیش‌فرض** + فیلد `Settings` +
   کنترل وب‌سایت + پیش‌فرض در mock + خط در `toml.example` + تست واحد +
   ظاهر شدن در `TEST_MATRIX.md` (از طریق `gen_status.py`، نه ویرایش دستی).
3. **هیچ ادعایی بدون خروجی واقعی اجرا.** عدد بدون خروجی دستور = نقض مستقیم.
4. گزارش نهایی طبق بخش ۹ `AI_RULES.md` (Changed / Verified / Not verified /
   Remaining / Regression / Final status) — به فارسی.
5. اگر بخشی از کار در این نشست تمام نشد، وضعیت دقیقش (`PARTIAL`/`BLOCKED`
   /…) در گزارش و در `STATUS.md` ثبت می‌شود؛ ادعای `DONE` فقط با مدرک.
